---
title: Installation
description: Install the package and open a database.
---

```bash
npm install @minnowdb/core
```

Plain JavaScript, no post-install step and no binary to fetch. It is around 185 KB gzipped —
roughly two-fifths of SQLite's WebAssembly build, which also has to download and compile its module
before it can answer anything.

The engine speaks SQL and needs nothing else. If you also want a typed query builder, add the
optional client:

```bash
npm install @minnowdb/client
```

It ships as its own package and uses the public plan-building tools at `@minnowdb/core/plan` — the
same ones any other builder can use. Every Minnow package shares a major version and moves
independently inside it. Each package records the oldest sibling release it needs, and npm chooses
a compatible version inside that major while refusing a mixed-major pair. See
[Versioning](/docs/reference/versioning).

## Entry points

| Import                           | What it is                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `@minnowdb/core`                 | The engine: `MinnowDatabase` and everything for running SQL in the current thread.                                |
| `@minnowdb/core/storage`         | Block stores: `IndexedDbBlockStore`, `OpfsBlockStore`, `MemoryBlockStore`, and the shared `BlockStore` interface. |
| `@minnowdb/core/storage/toolkit` | Building blocks for [writing storage adapters](/docs/storage/custom): `RecordCore`, the WAL and extent machinery. |
| `@minnowdb/core/worker`          | A ready-made worker entry. Point a module worker at it.                                                           |
| `@minnowdb/core/client`          | `MinnowDatabaseClient`, the main-thread half of the worker pair.                                                  |
| `@minnowdb/core/plan`            | Plan-building tools for a typed layer over the engine.                                                            |
| `@minnowdb/core/testing`         | Fault injection, deterministic simulation, SQLLogicTest, and the shared block-store test kit.                     |
| `@minnowdb/core/block-format`    | The on-disk block encoding, for tools that read blocks directly.                                                  |
| `@minnowdb/core/transactions`    | Lower-level snapshots, transactions, and recovery tools.                                                          |
| `@minnowdb/core/worker-protocol` | The messages used between the worker client and worker host.                                                      |
| `@minnowdb/client`               | Optional typed query builder: `createMinnow`, `InferDatabase`.                                                    |
| `@minnowdb/devtools`             | Optional SQL console and data browser for development or an embedded playground.                                  |

## Opening a database

A database is an engine plus a block store. The store decides where blocks live; everything else
is identical whichever one you choose.

```ts
import { MinnowDatabase } from "@minnowdb/core";
import { IndexedDbBlockStore } from "@minnowdb/core/storage";

const store = await IndexedDbBlockStore.open({ name: "shop" });
const db = new MinnowDatabase(store);
```

Inside a worker, [OPFS](/docs/storage/opfs) is the other durable choice — the same call against
a different floor:

```ts
import { OpfsBlockStore } from "@minnowdb/core/storage";

const db = new MinnowDatabase(await OpfsBlockStore.open({ name: "shop" }));
```

For tests and for data that should not outlive the page, swap in the in-memory store — it
uses the same interface, so nothing else changes:

```ts
import { MemoryBlockStore } from "@minnowdb/core/storage";

const db = new MinnowDatabase(new MemoryBlockStore());
```

See [Storage](/docs/storage) for what each adapter costs and guarantees.

## Where it runs

Anything with `CompressionStream` and a durable store: current Chrome, Firefox, Safari, and
Edge, in a window or a worker. [IndexedDB](/docs/storage/indexeddb) works everywhere;
[OPFS](/docs/storage/opfs) needs a worker and does not exist in Safari private browsing. There is
no Node build — the engine targets browsers, and the tests run it in real ones.

Most applications should [run the engine in a worker](/docs/engine/workers). Queries, writes,
migrations, live queries, snapshots, and maintenance use the same calls on either side, and query
execution then never competes with rendering.
