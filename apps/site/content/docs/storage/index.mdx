A database is an engine plus a store. The engine decides what to write; the store decides where it
goes. Three adapters ship today, all implementing the same `BlockStore` contract, so swapping one
for another changes nothing else about your code.

| Adapter                                          | Import                   | Survives a reload | Use it for                                         |
| ------------------------------------------------ | ------------------------ | ----------------- | -------------------------------------------------- |
| [`IndexedDbBlockStore`](/docs/storage/indexeddb) | `@minnowdb/core/storage` | Yes               | Applications.                                      |
| [`OpfsBlockStore`](/docs/storage/opfs)           | `@minnowdb/core/storage` | Yes               | Applications, where OPFS exists (worker required). |
| [`MemoryBlockStore`](/docs/storage/memory)       | `@minnowdb/core/storage` | No                | Tests, scratch work, throwaway analysis.           |

The two durable adapters hold the same block format, and a [snapshot](/docs/storage/snapshots)
moves a database between them. Speed is measured live on the [benchmarks page](/benchmarks)
rather than asserted here — on current engines the OPFS adapter's small reads and writes
measure several times faster. Where OPFS is unavailable — notably Safari private browsing —
IndexedDB is the fallback, and it remains the default.

## What a store holds

Not rows. The engine hands the store immutable, compressed, self-describing **blocks** — one
column's values for one row group — plus the records that say which blocks are live:

- **Blocks** — the data, keyed by an immutable id.
- **Manifests** — which block ids are live at each version. Publishing a manifest is what makes a
  commit visible.
- **Segments** — which blocks belong to which table, and which row ids they cover.
- **Transactions** — the commit each segment belongs to, which is how visibility resolves.
- **Catalog** — tables, columns, counters, unique-key membership, full-text index state.
- **Leases, temp pages, and job records** — reader pins, query spill, and the cursors that let
  compaction and collection resume.

Because published blocks are immutable and a version is just a set of block ids, a reader can hold
a version open while writers keep committing. That is the whole concurrency story, and it is a
property of this layout rather than of any locking.

## Writing your own

`BlockStore` is a public, documented contract — seven capability interfaces, a rulebook in
their TSDoc, and a conformance kit (`blockStoreConformanceCases` from `@minnowdb/core/testing`)
that checks an implementation against every rule the shipped adapters answer to. Implementing
it against another substrate — React Native storage, an object store, the Node filesystem, an
encrypted wrapper — gives you a working database with no engine changes. You do not start from
a blank interface either: `@minnowdb/core/storage/toolkit` publishes the record-semantics core
and the write-ahead-log machinery the shipped adapters themselves are assembled from.
[Writing a storage adapter](/docs/storage/custom) is the guide.

## Moving data between stores

A [snapshot](/docs/storage/snapshots) copies one committed version out as a single portable file
and loads it into any store — memory to IndexedDB, one browser to another, or a build script to a
published asset.
