---
title: Offline sync and rekeying
description: Changing a row's primary key when a record created offline gets its server key, and what the engine does so nothing holding the old key loses the row.
---

An app that works offline creates records before the server has seen them. The record needs a
key right away, so the app makes up a temporary one. When the record syncs, the server answers with
its own key, and the row has to move to it. Everything that held the old key — child rows, open
forms, list selections, queued requests, other tabs — has to keep finding the row.

Minnow handles this with one rule: **a row has one key, its primary key, and you can change it
with an ordinary `UPDATE`.** The engine moves the row, moves every reference to it in the same
commit, and remembers the old key so it keeps working for a while. There is no second id column to
join on. Application state can follow key-change notifications; keys persisted outside Minnow
resolve through the engine before use.

## A record made offline

The examples use the [retail dataset](/#console). In it, `order_items.order_id` and
`returns.order_id` are declared to reference `orders.order_id`. They are declared with
`enforced: false`, which keeps the relationship without requiring the parent row to exist; see
[declaring references](#declaring-references).

A customer places an order while the device is offline. The app gives it a temporary key that can
never be a real server key — here a negative number:

```sql
INSERT INTO orders (order_id, customer_id, store_id, channel, status, payment_method,
  item_count, subtotal, discount, tax, shipping, total, placed_at)
VALUES (-1, 1, 1, 'online', 'placed', 'card', 1, 20, 0, 1.6, 0, 21.6, now());

INSERT INTO order_items (order_item_id, order_id, product_id, quantity, unit_price, discount, line_total)
VALUES (-1, -1, 1, 1, 20, 0, 20);
```

## The sync

The device comes back online, pushes the order, and the server answers that the order's real key
is `900001`. The app rekeys the row:

```sql
UPDATE orders SET order_id = 900001 WHERE order_id = -1;
```

That is the whole sync step. The line item now says `order_id = 900001` too:

```sql
SELECT order_item_id, order_id FROM order_items WHERE order_item_id = -1;
```

The batch API and Kysely do the same thing: `db.update("orders", -1, { order_id: 900001 })`, or
`db.updateTable("orders").set({ order_id: 900001 }).where("order_id", "=", -1)`.

## What the engine does

For that one `UPDATE`, in order:

1. **Takes the writer turn.** The rekey is one write scope, like any other write. No other write,
   in this tab or another, runs in the middle of it.
2. **Finds the row and checks the new key.** The new key must not be taken by another row, must
   not be null, and must not be a key that was itself retired by an earlier rekey (see below). If
   any check fails, nothing is written.
3. **Fires `BEFORE UPDATE` triggers**, with the old row as `OLD` and the moved row as `NEW`.
4. **Moves the row.** Underneath, a row lives at its key, so the engine removes it from the old key
   and writes it at the new one, with every other column unchanged. Indexes, `UNIQUE` columns,
   full-text indexes, and stored generated columns follow, exactly as for a delete and an insert.
5. **Moves every reference.** For each declared foreign key that points at the table — enforced or
   not — the engine finds the rows holding the old key and updates them to the new key. If that
   column is also part of the child's own primary key, the child is rekeyed the same way, and its
   own references follow, up to eight levels deep; a deeper chain is refused and nothing is
   written. A row that refers to its own table, or to itself, is handled too.
6. **Records a forward** from the old key to the new one, in an internal table. A forward is never
   changed once written. If the row was rekeyed before, its older forwards stay as they are and
   lead here through this one: `-1 → 900001`, then `900001 → 900002`, and `-1` follows both.
7. **Fires `AFTER UPDATE` triggers.** `INSERT` and `DELETE` triggers do not fire: to the
   application this is one update.
8. **Commits once.** The row, its references, and the forward publish together. A crash before the
   commit leaves none of them; after it, all of them.
9. **Other tabs catch up.** The commit reaches other tabs and workers the way every commit does.
   Because the forward is stored data, a tab that missed the notification — a sleeping tab, a
   dropped message — still sees it the next time it reads.
10. **Live queries update together.** Every live query the commit changed gets its new result in the
    same turn, with a `keyChanges` list naming the rekeyed row. See
    [live queries](#live-queries-and-held-keys).

## The old key keeps working

For 10 days after the rekey (the `keyForwardRetentionMs` option), the old key is an alias of the
row. Whenever a key value is compared by equality or written — a primary key or a foreign key, in
SQL or through the batch API — the engine swaps a retired key for the current one first.

```sql
SELECT order_id, total FROM orders WHERE order_id = -1;
UPDATE orders SET status = 'shipped' WHERE order_id = -1;
SELECT count(*) FROM order_items WHERE order_id = -1;
```

The first query returns the order, with `order_id` 900001. The update changes order 900001, and
the count finds its line item.

| What happens after the rekey                               | Result                                            |
| ---------------------------------------------------------- | ------------------------------------------------- |
| `SELECT`, `UPDATE`, `DELETE` with `WHERE order_id = -1`    | Acts on row `900001`                              |
| `update`, `delete`, `updateBatch`, `deleteBatch` with `-1` | Acts on row `900001`                              |
| An upsert, or `INSERT … ON CONFLICT`, naming `-1`          | Updates row `900001`; never a second row          |
| A plain `INSERT` of an order with key `-1`                 | Refused as a duplicate: the old key is still held |
| A new line item written with `order_id = -1`               | Stored as `order_id = 900001`                     |
| Rekeying any row onto `-1`                                 | Refused as a duplicate                            |
| A row evicted and synced back as `900001`                  | `-1` still reaches it                             |

Some things to know:

- **Stored rows only hold current keys.** The swap happens when a value is written, so joins,
  ranges, and `LIKE` work on the stored keys and never need the forwards. Only a comparison of a
  key with a constant or a parameter follows a retired key: equality (`=`, `IN`,
  `IS NOT DISTINCT FROM`) and its opposite (`<>`, `NOT IN`, `IS DISTINCT FROM`), with the value
  negated or not (`-1`, `-$1`). It is followed anywhere in a `WHERE`, `HAVING`, or `ON` clause —
  under `AND`, `OR`, `NOT`, and `IS NULL` too, so `WHERE id = -1` and `WHERE NOT (id = -1)`
  always split the rows between them — and in any part of the statement: subqueries, derived
  tables, CTEs, and views included. A view column that passes a key column through counts as that
  key column.
- **A composite key** is followed when the query pins every one of its columns with `=` on the same
  table reference, as in `WHERE shop = 1 AND receipt = -1`.
- **The result shows the current key.** `WHERE order_id = -1` returns a row whose `order_id` is
  `900001`. That is on purpose, like a redirect, and it is how a screen holding the old key learns
  the new one.
- **Tables that are never rekeyed** have no forwards and behave as plain SQL. Checking for a
  forward costs one in-memory lookup, and nothing at all until the first rekey.
- **A swap is allowed.** Rekeying two rows onto each other's keys in one statement moves both rows,
  and neither key forwards, since both are still in use.

### How long forwards last

`keyForwardRetentionMs` sets how long an old key forwards; the default is 10 days. After that, the
old key is unknown again: a read finds nothing, and the key may be used for a new row. Background
maintenance deletes expired forwards; `collectGarbage()` deletes them too. A live query that named
an expired key keeps its last result until one of its tables changes or maintenance deletes the
forward.

A row rekeyed more than once is reached from every key it had. Each rekey keeps its own forward
with its own expiry, and a lookup follows them one after another while each is still within
retention. An old key stops forwarding when its own forward expires; a later key keeps forwarding
until its forward expires.

A forward outlives its row. If order `900001` is deleted and a different row is later written with
key `900001`, the old key `-1` names that row until the forward expires. Temporary keys that are
never reused, as below, keep this from mattering.

A forward takes about 100 bytes on disk, and only rows that were rekeyed have one. A database that
is written to constantly but never rekeys keeps none. Each connection also keeps the forwards in
memory, about 0.75 KB each: 7 MB for 10,000. A connection reads them once, the first time it needs
them, in slices that leave the page responsive (about 0.35 s for 100,000). After that it updates
them from the rows each commit wrote, so a rekey costs the forwards it made, not every forward
held, and deleting expired ones reads no more than they are.

The retention is fixed on each forward when it is written. Changing `keyForwardRetentionMs`
affects forwards written afterwards; forwards already stored keep the expiry they were given, so
every connection agrees on when a key stops forwarding.

## Live queries and held keys

**One commit, one update.** When a commit changes several live queries, they all get their new
results in the same turn. A React component that reads a list and a detail form therefore never
renders a moment where the list shows the new key and the form the old one. Across a worker, the
results cross as one message. This covers low-level subscriptions and typed queries whose adapter
decodes the engine's result; see [live queries](/docs/extensions/live-queries) for the details and
the cost.

**`keyChanges`.** A delivery that follows a rekey carries each rekey it covers, as the step it
made:

```ts
live.subscribe("SELECT order_id, status FROM orders WHERE customer_id = 1", {
  onChange(result, delivery) {
    // [{ table: "orders", from: -1, to: 900001 }]
    for (const change of delivery.keyChanges ?? []) rename(change.from, change.to);
  },
});
```

The list is read from the stored forwards, so it is complete even for a tab that missed the
cross-tab notification. A row rekeyed twice between two deliveries appears as two steps, in commit
order (`-1 → 900001`, `900001 → 900002`); applying them in order renames a held key all the way.
Typed live queries carry the same `keyChanges` on their `ready` snapshot.

**Keyed diffs.** A keyed live query that names its table —
`live.changes(query, { key: "order_id", table: "orders" })` — reports a rekeyed row as one change,
`{ type: "rekey", from, key, row, previous, previousIndex, index }`, instead of a delete and an
insert, following several steps when the row moved more than once. A list renderer can keep the
row's component, and its selection, under the new key.

**Holding a key in a screen.** The simplest way to follow a record is to keep querying it by the
key you have. A detail view running `SELECT * FROM orders WHERE order_id = ?` with `-1` keeps
showing the order after the rekey, and the row's `order_id` column tells you the current key.

**Keys held outside a query** — a URL, a cache, a queued request — resolve with `resolveKey`:

```ts
await db.resolveKey("orders", -1); // 900001
await db.resolveKey("receipts", [1, -1]); // a composite key, in primary-key order
```

## When the server row already exists

A sync page may bring in the server row before the acknowledgement of an offline insert arrives.
Once the application knows the two keys name the same record, merge the temporary row into the
existing server row:

```ts
await db.mergeKey("orders", -1, 900001);
// Also available through MinnowDatabaseClient and a write() session.
```

Both rows must exist, after following any current forwards. The target row keeps its values,
including columns the application did not read. Every declared reference to the source moves to
the target, enforced or not. The source disappears and its key forwards to the target for the
usual retention period. These changes publish in one transaction. References within the target
row follow too, so a target column referencing the source changes to the target key.

`mergeKey` requires an explicit identity match from the application; it does not infer one from
row values. A normal `UPDATE` onto an occupied key still throws `UniqueConstraintError`.
Composite keys use arrays in primary-key order. A missing source or target throws `MissingKeyError`;
a source that already forwards to the existing target is a no-op, so an acknowledged merge can
be retried while its forward remains valid. Merging an existing key into itself is also a no-op.

A child whose reference is part of its own primary key rekeys in turn. A child-key collision,
failed constraint, trigger failure, or cascade that would change the source or target key aborts
the whole merge. Source and target rows do not fire DELETE or UPDATE triggers for the merge;
referencing rows use the normal update and rekey paths, including their UPDATE triggers.
ON DELETE actions do not run. A keyed live result containing both rows reports the source's
deletion and retains the target, rather than reporting a rekey onto an existing result key.

## Resolving queued keys together

`resolveKeys(table, keys)` returns an array in input order, preserving duplicate inputs. It uses
one captured forward generation for the whole batch and, through the worker client, one request:

```ts
await client.resolveKeys("orders", [-1, -2, -1]);
await client.resolveKeys("receipts", [
  [1, -1],
  [1, -2],
]);
```

Each result has the same shape and meaning as `resolveKey`: scalar keys remain scalar, composite
keys remain arrays, and a key without an active forward comes back unchanged. This does not prove
that a row exists. After retention expires an old key can no longer identify the original row.
An external outbox must resolve or durably update its held keys within that window, or retain an
application reconciliation strategy. Keeping outbox references inside Minnow lets rekeying move
them in the same transaction as the record.

## Following keys held in application state

Subscribe once on the worker client to learn future rekeys across every table:

```ts
const unsubscribe = await client.onKeyChanges(
  (changes) => {
    for (const change of changes) {
      renameHeldKey(change.table, change.from, change.to);
    }
  },
  { onError: reportError },
);

// When the screen or owning service closes:
await unsubscribe();
```

Await registration before making writes whose notifications you need. Notifications arrive once
per observed rekey, in order within a sweep, even when no query reads that table, a query's rows
stay unchanged, or no live queries exist. Several commits can coalesce into one sweep. Overlapping
live sets are deduplicated. The first live set to observe a rekey sends its notice before any
query results in that worker message. Other live sets sweep independently and do not repeat the
notice; use one set for queries that must update together. A listener's exception reaches its
`onError` without preventing other listeners or query deliveries.

The subscription observes retained durable forwards, with a one-second polling fallback for
missed hints. It starts with a baseline and does not replay earlier rekeys. Rekeys whose forwards
expired before observation cannot be recovered from notifications. Swaps and rotations that leave
keys in use create no forwards and produce no notice; follow query results for those operations.
Listener handles end on client
close or connection loss; register them again after `reopen()`. Unsubscribing is idempotent.

A synchronous UI lookup may keep a session map from these notices. That map describes observed
changes; clear it when its database or table is replaced. It cannot establish the current key for
an unseen or expired forward. Resolve persisted
keys asynchronously on startup, and use `resolveKey` or `resolveKeys` when an authoritative lookup
is needed. Low-level engine users can observe the same future changes with
`await live.subscribeKeyChanges(listener)` and close the returned subscription, independently of
query-result delivery.

## Declaring references

A rekey moves the references the catalog knows about, so declare them. A reference always follows
a rekey; there is no option to turn that off.

```ts
// Checked: the parent row must exist.
order_id: column.number().references("orders", "order_id"),

// Unchecked: the parent may not be in this database.
order_id: column.number().references("orders", "order_id", { enforced: false }),
```

|                               | Checked (default)         | Unchecked (`enforced: false`) |
| ----------------------------- | ------------------------- | ----------------------------- |
| A row whose parent is missing | Refused                   | Allowed                       |
| The parent is deleted         | Its `onDelete` action     | Nothing happens to the rows   |
| The parent is rekeyed         | The rows follow           | The rows follow               |
| A value naming a retired key  | Stored as the current key | Stored as the current key     |

Use unchecked references when the database holds only part of the parent table. An app that syncs
orders for a date window may hold line items whose order is outside the window.

In SQL the same choices are `REFERENCES orders (order_id)` and
`REFERENCES orders (order_id) NOT ENFORCED`. `ON UPDATE CASCADE` is accepted, since it states what
happens anyway. `ON UPDATE RESTRICT`, `NO ACTION`, `SET NULL`, and `SET DEFAULT` are refused,
because a reference always follows. This differs from PostgreSQL, where a referenced key cannot
change by default.

A table that references a rekeyed table needs a primary key of its own, so the engine can update
its rows. A rekey whose references cannot be moved is refused, and nothing is written.

## Choosing temporary keys

- **A temporary key must never equal a real one.** Use a range the server never hands out:
  negative numbers for integer keys, or a prefix such as `o:` for text keys. If a temporary key
  could equal a server key, the server's row would collide with it.
- **Fix old temporary keys with a rekey.** If an app already stored offline keys that look like
  server keys, rekey them into the safe range once: `UPDATE tickets SET id = 'o:' || id WHERE …`.
  Their references follow.
- **Point queued work at rows through references.** An outbox row that references the order through
  a declared foreign key is moved by the rekey itself and never depends on the forward. Payloads
  that keep a key as plain text can resolve it with `resolveKey` before sending.
- **Forwards are local.** They live in this device's database and are not synced. Each device keeps
  the forwards for the rekeys it ran or received.
