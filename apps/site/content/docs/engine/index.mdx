`MinnowDatabase` is the engine. It takes a [block store](/docs/storage) and exposes everything
else — SQL, batch writes, the catalog, and maintenance.

```ts
import { MinnowDatabase } from "@minnowdb/core";
import { IndexedDbBlockStore } from "@minnowdb/core/storage";

const store = await IndexedDbBlockStore.open({ name: "shop" });
const db = new MinnowDatabase(store, {
  compression: "gzip",
  bufferPoolBytes: 64 * 1024 * 1024,
});
```

When the engine [runs in a worker](/docs/engine/workers), `MinnowDatabaseClient` offers the same
query, write, migration, live-query, snapshot, and maintenance calls on the main thread. The
direct `createView`, `dropView`, and `buildFtsIndex` helpers stay on `MinnowDatabase`; migrations
manage views in a worker, and full-text indexes still build automatically.

## Catalog

```ts
await db.createTable({
  name: "orders",
  uniqueKey: "order_id",
  columns: [
    { name: "order_id", type: "number" },
    { name: "total", type: "number" },
    { name: "note", type: "string", nullable: true },
  ],
});

await db.listTables();
```

`createTable` is the direct API form of [`CREATE TABLE`](/docs/sql/ddl). The schema builder and
SQL can declare defaults too; use whichever form fits the rest of your setup.

## Bulk writes

Parsing an `INSERT` per row is the wrong shape for loading data. The batch APIs take rows
directly:

```ts
await db.insertBatch("orders", [
  { order_id: 1, total: 24.5, note: null },
  { order_id: 2, total: 88.0, note: "gift wrap" },
]);
```

Or columns, when you already hold them that way — which skips the pivot the engine would
otherwise do:

```ts
await db.insertBatch("orders", {
  columns: {
    order_id: [1, 2],
    total: [24.5, 88.0],
    note: [null, "gift wrap"],
  },
});
```

The full set:

| Call                                    | Effect                                               |
| --------------------------------------- | ---------------------------------------------------- |
| `insertBatch(table, input)`             | Append rows. A duplicate key throws.                 |
| `upsertBatch(table, input)`             | Insert, replacing any row with the same key.         |
| `updateBatch(table, { keys, changes })` | Change named columns on rows addressed by key.       |
| `deleteBatch(table, { keys })`          | Remove rows by key.                                  |
| `insert` / `upsert` / `update`          | Single-row convenience wrappers over the same paths. |

Each returns what it did — `rowCount`, `blockCount`, `storedBytes`, and the published `version` —
which is enough to drive a progress bar over a large load without a second query.

One batch is one commit. To make several land together, wrap them in a
[write scope](/docs/engine/transactions).

### Buffered writing

For a stream of small writes — telemetry, edits as a user types — a buffered writer combines them
into blocks worth committing:

```ts
const writer = db.bufferedWriter("events", { maxRows: 5_000, maxAgeMs: 250 });
await writer.add({ event_id: id, kind: "click", at: new Date() });
await writer.flush();
```

`attachLifecycleFlush` wires a writer's flush to page hide and freeze events, so a buffer does not
follow the tab into the grave.

## Options

| Option                     | Default       | What it does                                                                                                                                                                        |
| -------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `compression`              | `"gzip"`      | Block encoding. `"raw"` writes faster; `gzip` usually uses about half the storage and can make a cold read faster because the browser fetches fewer bytes.                          |
| `rowsPerBlock`             | `65536`       | How many rows Minnow aims to put in each block. Smaller blocks can help narrow reads but add more work to broad scans.                                                              |
| `bufferPoolBytes`          | 64 MiB        | Space kept for decoded blocks and reusable query work. `0` disables the cache. Cached data is tied to the exact block or table version, so an old entry is never used for new data. |
| `ftsAutoIndexRows`         | `4096`        | Row count above which `MATCH` can schedule a background index build for a column that does not have one yet.                                                                        |
| `maxCommitRetries`         | `8`           | How many times a write retries after another tab publishes first.                                                                                                                   |
| `spillOwnerLeaseMs`        | `60000`       | How long temporary query files stay claimed between renewals while a query is running.                                                                                              |
| `transactionIdleTimeoutMs` | `30000`       | How long an untouched `BEGIN` transaction may remain open before Minnow rolls it back. This prevents an abandoned transaction from keeping storage alive forever.                   |
| `autoCompact`              | `true`        | Whether Minnow combines fragmented tables in the background; see [compaction](/docs/storage/maintenance).                                                                           |
| `autoCollect`              | `autoCompact` | Whether Minnow removes replaced blocks and old versions in the background; see [garbage collection](/docs/storage/maintenance#garbage-collection).                                  |
| `compaction`               | `{}`          | Defaults for every compaction job, including background work. `partitionRows` defaults to 16,384. See [partitioned folds](/docs/storage/maintenance#partitioned-folds).             |

The stock worker accepts the options that can be copied in its startup message: `compression`,
`rowsPerBlock`, `maxCommitRetries`, `spillOwnerLeaseMs`, and `bufferPoolBytes`. It uses defaults for
the others. A [custom worker entry](/docs/engine/workers#custom-worker-entries) can construct
`MinnowDatabase` with the full option set.

## Errors

Errors are classes, so they can be caught by kind rather than by matching a message:

```ts
import { SqlCompileError, UniqueConstraintError } from "@minnowdb/core";
import { WriteConflictError } from "@minnowdb/core/storage";
```

`SqlCompileError` carries the `offset` and `length` of the offending span, which is what the
devtools editor underlines. `WriteConflictError` means a writer in another tab, or a write scope,
committed first; the engine retries these itself up to `maxCommitRetries` before surfacing one.

## Closing

```ts
await db.close();
store.close();
```

`db.close()` rolls back an open `BEGIN`, stops live-query polling and background scheduling,
releases the engine's reader lease, and drops resident caches. `MinnowDatabase` does not take
ownership of the injected store, so close it second. A `MinnowDatabaseClient` performs both steps
when you call `await client.close()`; pass `{ terminateWorker: true }` when its dedicated worker
has no other job.
