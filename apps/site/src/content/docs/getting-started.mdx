# Getting started

<p class="lede">
  Install the package, declare a schema, and you have a typed SQL database running in the browser —
  no server, no WASM file, no build step. This page takes you from install to queries, workers, and
  tests.
</p>

```bash
npm install @minnowdb/core
```

> Minnow is experimental. The storage format may still change, and the SQL surface is a
> correctness-first subset — every supported form is listed in the [feature matrix](/docs/sql/).

## Column types

There are four, on purpose:

- `boolean`
- `number`
- `string`
- `datetime`

Storage details like numeric width and encoding are the engine's problem, not schema choices. Row
IDs are assigned internally.

## First session

Declare a schema, open a store, migrate, and query. One declaration drives migrations,
autocomplete, row types, typed writes, and [live queries](/docs/live-queries/):

```ts
import {
  MinnowDatabase,
  createMinnow,
  column,
  schema,
  table,
  type InferDatabase,
} from "@minnowdb/core";
import { IndexedDbBlockStore } from "@minnowdb/core/storage";

const people = table("people", {
  name: column.string().unique(),
  score: column.number(),
  joined: column.datetime().nullable(),
});
const appSchema = schema([people]);
interface DB extends InferDatabase<typeof appSchema> {}

const store = await IndexedDbBlockStore.open({ name: "app-db" });
const database = new MinnowDatabase(store);
await database.migrate(appSchema);

const db = createMinnow<DB>(database, { schema: appSchema });

const written = await db
  .insertInto("people")
  .values([
    { name: "Ada", score: 10, joined: new Date() },
    { name: "Grace", score: 20 }, // joined pads to null
  ])
  .returningAll()
  .execute();

const rows = await db
  .selectFrom("people")
  .where("score", ">=", 10)
  .select(["name", "joined"])
  .orderBy("name")
  .execute(); // Array<{ name: string; joined: Date | null }>
```

Two things are true of every write:

- It **validates before storing anything** — column names, types, nulls, row counts.
- It **publishes atomically** — a reader in another tab sees the old version or the new one,
  never a partial write.

## The SQL and batch layer

The builders compile onto raw SQL and column batches. Use that layer directly for bulk loads and
ad-hoc SQL:

```ts
await database.insertBatch("people", {
  columns: {
    name: ["Katherine", "Linus"],
    score: [30, 25],
    joined: [new Date(), null],
  },
});

const resultSet = await database.query(`
  SELECT score, COUNT(*) AS people
  FROM people
  WHERE score >= 20
  GROUP BY score
  ORDER BY score DESC
`);
```

Same engine, same plans — a builder query and its SQL equivalent execute identically. See
[Writes & transactions](/docs/writes/) for the full batch API.

## Run it in a worker

The engine runs wherever you construct it. The examples on the [home page](/) run it on the main
thread against an in-memory store, and the code is identical either way because the whole API is
async.

For real datasets, use a worker — decoding and query execution are heavy enough to jank the main
thread. Minnow ships both sides; you add one line, the `Worker` itself:

```ts
import { MinnowDatabaseClient } from "@minnowdb/core/client";

const client = new MinnowDatabaseClient(
  new Worker(new URL("@minnowdb/core/worker", import.meta.url), { type: "module" }),
  { store: { kind: "indexeddb", name: "app-db" } },
);
await client.migrate(appSchema);
const db = createMinnow<DB>(client, { schema: appSchema });
// …exactly the same code as above
```

See [Workers & multi-tab](/docs/workers/) for the full client, bundler setups, and custom worker
entries.

## Testing

Swap in `MemoryBlockStore` and your tests run the real engine — tables, queries, compaction, all
of it — without touching browser storage:

```ts
import { MemoryBlockStore } from "@minnowdb/core/storage";

const database = new MinnowDatabase(new MemoryBlockStore());
```
