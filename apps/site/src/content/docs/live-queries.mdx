# Live queries

<p class="lede">
  Subscribe to a query and get fresh rows after every commit that could change it — including
  commits from other tabs. A missed notification can delay a refresh; it can never produce a stale
  result.
</p>

## Typed live queries

Any [built query](/docs/queries/) becomes live with `.live()`. Subscribers get the current rows
immediately, then a fresh result after relevant commits:

```ts
const live = db.selectFrom("people").select(["name"]).where("score", ">", 15).live();

const sub = await live.subscribe({
  onChange: (rows) => render(rows), // rows: Array<{ name: string }>
  onComplete: () => {}, // optional: the live set closed
});
// or, latest-wins async iteration:
for await (const rows of live) render(rows);

await sub.close();
await db.close(); // closes the shared live set; open iterators end cleanly
```

- **Iteration ends promptly** on `break`, `iterator.return()`, or when the live set closes — a
  cancelled iterator never waits for the next commit.
- **Iteration is latest-wins.** Every yielded value is a true snapshot, but a slow consumer skips
  intermediate results rather than falling behind.
- **Configure once, on the facade:**
  `createMinnow<DB>(driver, { schema, live: { channelName: "app-commits", pollIntervalMs: 5000 } })`.

## Subscribing with SQL

The underlying mechanism also takes raw SQL:

```ts
const live = database.liveQueries({ channelName: "db", pollIntervalMs: 5_000 });
const subscription = await live.subscribe(
  "SELECT status, COUNT(*) AS orders FROM orders GROUP BY status",
  { onChange: (result) => render(result) },
);
// later: subscription.close(); live.close();
```

## Why results can't go stale

Every commit records which tables changed, durably, before any notification goes out. Four things
can prompt a re-check:

- a local commit in the same database instance;
- a cross-tab BroadcastChannel message;
- a poll tick;
- an explicit `refresh()`.

All four converge on the same durable version. The notifications are only accelerants — the
recorded change sets are authoritative — so a dropped message or a suspended tab delays a refresh
but can't make a subscriber show stale data.

## What a subscription costs

Not much, by design:

- A subscription keeps its query, its dependency table IDs, and a numeric digest of the last
  result — **never rows**.
- Re-runs are skipped when none of the query's tables changed, and also when the data layer can
  _prove_ the commits could not change the result — every new block's zone statistics reject the
  query's predicates. The proof is deliberately narrow: a query that reads the same table again
  through a subquery, `EXISTS`/`IN`, CTE, or derived table always re-runs, because a row the
  predicates reject can still move a value such a read produces. So can a commit whose segments
  were compacted away and reclaimed before the sweep saw them.
- Notifications are suppressed when a re-run produces an unchanged digest, so `onChange` fires
  only when the result actually differs.
- `live.stats` reports all of it: hints received, sweeps, re-runs executed and avoided,
  suppressed notifications, sweep latency.

## Limitations

Change detection re-executes the query — there's no incremental view maintenance yet. When that
lands it will be added only for operator shapes proven safe, with full re-execution kept as the
baseline it's checked against. Subscriptions accept anything the read surface executes: built
queries or the same read-only SQL subset as `query()` — see [SQL support](/docs/sql/).
