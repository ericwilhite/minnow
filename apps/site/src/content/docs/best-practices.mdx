# Best practices

<p class="lede">
  Minnow is built around a few habits. Follow them and the failure you see in development is the
  same one you would have seen in production.
</p>

## Run the database in a worker

The engine runs wherever you construct it, but decoding blocks and executing queries takes real
CPU time. In production:

- Construct the database in a worker; keep only the [client proxy](/docs/workers/) on the main
  thread. It's a three-line setup and the typed facade works identically over both.
- Save main-thread construction for tests and prototypes.

## Declare the schema once, work typed

One `schema([...])` declaration drives migrations, autocomplete, row types, typed writes, and live
queries. The standard construction:

```ts
interface DB extends InferDatabase<typeof appSchema> {}
const db = createMinnow<DB>(database, { schema: appSchema });
```

- **The named interface is what keeps the editor pleasant.** Hovers, errors, and generated
  declarations print `Minnow<DB>` instead of the expanded schema, which grows with every table.
- **Do it once, in one module.** Put the schema, `DB`, and `db` in a `db.ts` and export them —
  the rest of the app never sees the construction line.
- `createMinnow(database, { schema })` without the type argument infers `DB` from the schema
  value. Fine for scratch code; expanded types in tooling otherwise.

The raw layer (`database.query()`, `insertBatch()`, the `sql` tag) is the same pipeline, not a
second engine — builder queries compile to the exact plans their SQL equivalents produce, so
switching layers never changes behavior.

## Write in batches, not loops

Every commit publishes data and updates the manifest; a loop of single-row inserts pays that full
cost per row. Hand the engine the whole batch, or let the buffered writer batch for you:

```ts
// Bulk load: one commit for every row.
await database.insertBatch("events", events);

// Already holding columns? Pass them and skip the pivot.
await database.insertBatch("events", { columns: { id: ids, at: dates, kind: kinds } });

// Event streams: rows in, batches out.
const writer = database.bufferedWriter("events", {
  mode: "upsert",
  maxRows: 1_000,
  maxAgeMs: 1_000,
  onError: (error) => report(error),
});
await writer.add(event);
```

## Don't trust page unload

`attachLifecycleFlush()` flushes buffered writers when the tab hides. Use it — but it's an
optimization, not a guarantee. Durability ends at a committed IndexedDB transaction, and nothing
in `pagehide` changes that. Data that must survive belongs in a committed batch, not in a buffer
you hope will flush.

## Give big queries a memory budget

Without a budget, a large sort or join takes whatever memory it needs — possibly the whole tab.
With one, the engine spills to disk or fails with a typed error instead:

```ts
try {
  const result = await database.query(bigSql, { executionMemoryBudgetBytes: 64 * 1024 * 1024 });
} catch (error) {
  if (error instanceof QueryMemoryBudgetError) {
    // narrow the query, raise the budget, or page through smaller slices
  }
}
```

If tabs can die mid-query, run `cleanupQuerySpill()` occasionally to reclaim abandoned spill
pages.

## Expect write conflicts

Several tabs writing at once is a designed-for case. When two commits race, one wins and the other
fails with a typed error — never silent interleaving.

- The engine retries transparently where that's safe (`maxCommitRetries`).
- What reaches your code — `UniqueConstraintError`, a commit conflict — is the case that needs an
  application decision. Catch it and retry or merge where you know what's right.

## Treat migrations as additive

`migrate()` only performs safe, metadata-only steps. It rejects type changes, drops, unique-key
changes, and non-null tightening outright. So:

- Add columns as nullable.
- Rename with `.renamedFrom()` — a metadata step, not a drop-and-add.
- If a truly breaking change is unavoidable, that's a new table plus a deliberate copy.

## Close what you open

Live subscriptions, buffered writers, and live sets all have `close()`. On the worker client,
`close({ terminateWorker: true })` tears down everything. Queries themselves have no lifecycle:
every `query()` is fresh, and the only pinning primitive is the `snapshot()` scope, which
releases itself when its callback returns — keep those scopes short so cleanup is never held
back.

## Schedule maintenance in idle time

Compaction largely schedules itself: a scan that observes a heavily fragmented table (48+
visible segments) kicks off one incremental compaction step in the background, the same way
full-text indexes build themselves. Set `autoCompact: false` to opt out. Garbage collection —
and compaction beyond the automatic nudge — still advance in small, durable steps that survive
a tab closing mid-job; run them when the app is quiet:

```ts
requestIdleCallback(async () => {
  await database.compactTableStep("events", { maxBlocks: 1 });
  await database.collectGarbageStep({ maxItems: 8 });
});
```

There's no penalty for stopping — a resumed job continues from its checkpoint.

## Test against the real engine

`MemoryBlockStore` implements the full storage interface, so unit tests run the actual planner,
executor, and compaction with no browser storage. For crash testing, `FaultInjectingBlockStore`
throws at named points around block writes and commits:

```ts
import { MemoryBlockStore } from "@minnowdb/core/storage";
import { FaultInjectingBlockStore } from "@minnowdb/core/testing";

const store = new FaultInjectingBlockStore(new MemoryBlockStore(), (point) => {
  if (point === "beforeManifestCommit") throw new Error("crash here");
});
```

If a test passes against a mock but fails against the engine, the engine was telling you
something.
