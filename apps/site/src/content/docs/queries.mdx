# Typed queries

<p class="lede">
  A Kysely-style builder: column names autocomplete, row types are inferred, and every query
  compiles to the same plan its SQL equivalent would — never to a SQL string.
</p>

## Setup

The facade wraps a database or the [worker client](/docs/workers/) — the API is identical over
both. Naming the database type `DB` keeps hovers and errors printing `Minnow<DB>` instead of the
expanded schema:

```ts
import { createMinnow, column, schema, table, type InferDatabase } from "@minnowdb/core";

const people = table("people", {
  name: column.string().unique(),
  score: column.number(),
  city: column.string().nullable(),
});
const orders = table("orders", {
  order_id: column.number().unique(),
  person: column.string().references("people", "name"),
  total: column.number(),
});
const appSchema = schema([people, orders]);
interface DB extends InferDatabase<typeof appSchema> {}

await database.migrate(appSchema);
const db = createMinnow<DB>(database, { schema: appSchema });
```

## Selects

```ts
const rows = await db
  .selectFrom("people as p")
  .innerJoin("orders as o", "o.person", "p.name")
  .where("p.score", ">", 10)
  .where((eb) => eb.or([eb("p.city", "=", "London"), eb("p.city", "is", null)]))
  .groupBy("p.name")
  .having((eb) => eb(eb.fn.countAll(), ">", 1))
  .select(["p.name"])
  .select((eb) => [eb.fn.sum("o.total").as("revenue")])
  .orderBy("revenue", "desc")
  .limit(10)
  .execute(); // Array<{ name: string; revenue: number | null }>
```

The conventions:

- **String left-hand sides are columns; right-hand sides are values.** To compare two columns,
  use `eb.ref("a.x")` or a join's `onRef`.
- **`select()` takes strings, an expression callback, or both** across repeated calls —
  `"p.name"`, `"p.name as owner"`; `selectAll()` is `SELECT *`.
- **Left-joined columns type as `| null`**, because that's what a left join returns.
- **Run with** `execute()`, `executeTakeFirst()`, `executeTakeFirstOrThrow()`; `compile()` gives
  the plan, [`.live()`](/docs/live-queries/) subscribes to it.

## Expressions

| Category         | Forms                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Comparisons      | `eb(lhs, op, rhs)` with `=`, `!=`, `<`, `<=`, `>`, `>=`, `like`, `not like`, `in`, `not in`, `is`, `is not`; `eb.between`, `eb.notBetween` |
| Boolean logic    | `eb.and([...])`, `eb.or([...])`, `eb.not(...)`                                                                                             |
| Arithmetic       | `eb(lhs, "+" \| "-" \| "*" \| "/", rhs)`, `eb.neg(...)`                                                                                    |
| Aggregates       | `eb.fn.count`, `countAll`, `sum`, `avg`, `min`, `max`; `fn.count(x).distinct()`                                                            |
| Scalar functions | `eb.fn.round`, `coalesce`, `dateTrunc`                                                                                                     |
| Windows          | `eb.rowNumber() / rank() / denseRank()` and aggregate `.over((o) => o.partitionBy(...).orderBy(...))`                                      |
| Conditionals     | `eb.case().when(...).then(...).else(...).end()`                                                                                            |
| Subqueries       | `eb.selectFrom(...)`, `eb.exists(...)`, and builders as `in` / comparison operands                                                         |
| Full-text search | `eb.match(columns, query)`, `eb.fn.bm25(columns, query)`, `.search(query)`                                                                 |

Result types don't lie: `sum` over an empty group is `null`, so its type is `number | null`.

SQL value behavior is deterministic across browsers: strings compare in Unicode codepoint order,
`LIKE` `_` matches one Unicode codepoint, and set operations treat `-0` and `0` as the same numeric
value. `ROUND(value, precision)` rounds halfway values away from zero; precision truncates to an
integer and is clamped to `0..30`, matching SQLite's supported range.

## Full-text search

Any column is searchable — no index DDL, no schema marking. A search treats the row as one
document: every query term must appear in _some_ listed column (`"*"` means every non-boolean
column), a term ending in `*` matches prefixes, and numbers and datetimes match through their
canonical text (`42`, or `2026 08` for August 2026 — a datetime renders as its ISO instant).
Matching is Unicode-aware and deterministic (NFKC + lowercase; CJK matches by character bigrams);
there is no stemming — use `*` prefixes instead.

```ts
// The one-liner: filter by match, order by BM25 relevance. The ordering expression desugars
// into a hidden select item, so the row shape is exactly what you selected.
const hits = await db
  .selectFrom("articles")
  .select(["title"])
  .search("quick fo*")
  .limit(10)
  .execute(); // Array<{ title: string }>

// Want the score? Select it — the ordering reuses the same expression, computed once:
await db
  .selectFrom("articles")
  .select((eb) => ["title", eb.fn.bm25(["title", "body"], "quick fox").as("score")])
  .where((eb) => eb.match(["title", "body"], "quick fox"))
  .orderBy("score", "desc")
  .execute();
// SELECT title, BM25(title, body) AGAINST 'quick fox' AS score FROM articles
// WHERE MATCH(title, body) AGAINST 'quick fox' ORDER BY score DESC

// Search every table at once; hits merge into one relevance-ranked list.
const everywhere = await db.search("quick fox", { limit: 20 });
// Array<{ table: string; row: {...}; score: number }>
```

Semantics worth knowing: a row whose listed columns are all NULL is _unknown_ (dropped by
`WHERE`, like `LIKE` on NULL); an empty query matches nothing; unmatched documents score `0`
under BM25 while all-NULL ones score NULL. Scans evaluate matches against each block's string
dictionary — every distinct value tokenizes once, rows compare integers — under the query memory
budget. BM25 corpus statistics come from the persisted index when one is ready (exact, no extra
scan) and from a one-time whole-scan pass otherwise, in which case the scoring query
materializes its scan.

Large append-only tables get a persisted index for free: once a searched table crosses ~4096
rows, a background build starts, inserts maintain it atomically with each commit, and MATCH
scans skip segments containing no candidates. The index is a pruning accelerator, never ground
truth — every candidate is re-verified, and any keyed mutation (or a tab that predates the
index) atomically invalidates it, so queries silently fall back to the scan and the index
rebuilds itself. `database.buildFtsIndex(table, column)` warms one up eagerly.

## Derived tables, CTEs, set operations

```ts
const spend = db
  .selectFrom("orders")
  .groupBy("person")
  .select((eb) => [eb.ref("person").as("person"), eb.fn.sum("total").as("total")]);

// As a derived table…
await db.selectFrom(spend.as("t")).where("t.total", ">", 10).select(["t.person"]).execute();

// …or as a CTE, joinable by name.
await db
  .with("spend", () => spend)
  .selectFrom("people as p")
  .innerJoin("spend", "spend.person", "p.name")
  .select(["p.name", "spend.total"])
  .execute();

// Set operations chain left to right; member row types must match.
await db
  .selectFrom("people")
  .select(["name"])
  .unionAll(db.selectFrom("orders").select(["person as name"]))
  .orderBy("name")
  .execute();
```

Derived and CTE columns stay fully checked — an unknown column on `"t."` is a compile error, same
as on a real table.

## One plan, two front ends

The builder and the SQL parser meet in the same plan-assembly code, so a builder query and its SQL
equivalent produce **identical** optimized plans — same validation errors, same rewrites, same
execution. Plan-equality tests enforce this shape by shape.

```
SQL -> lexer -> parser ----------------+
                                       +-> shared assembly -> optimizer -> physical plan
Typed builder -> compile() ------------+
```

### Filters that skip whole blocks

Columns are stored as blocks that each record the range of values they hold, so a filter the
engine can compare against that range skips every block it cannot match. Comparisons (`=`, `<`,
`BETWEEN`) and `IN` lists on a number or datetime column all narrow this way.

A run of equalities on one column is normalized into an `IN` list before planning, so these two
filters are the same query — write whichever reads better:

```sql
SELECT * FROM orders WHERE status = 'paid' OR status = 'shipped'
SELECT * FROM orders WHERE status IN ('paid', 'shipped')
```

A disjunction that mixes columns (`status = 'paid' OR total > 100`) cannot become a list, so it
is checked row by row. When one of those branches is selective, splitting the query and combining
with `UNION` lets each branch prune on its own.

## Parameters

Every SQL entry point takes `?` (positional) or `$1`-style (numbered) placeholders. Values bind
at execution — they are never spliced into the statement text:

```ts
const result = await database.query("SELECT name FROM people WHERE score >= $1 ORDER BY name", {
  params: [25],
});

await database.execute("UPDATE people SET score = ? WHERE name = ?", [40, "Ada"]);
```

The rules are strict on purpose:

- A statement uses either `?` or `$n`, never both. `$n` values may repeat; each `?` takes the
  next value in order.
- The parameter list must match the placeholder count exactly, and a statement with placeholders
  refuses to run without one.
- Any column value binds — including datetimes with full time precision, which SQL text can only
  write as `DATE` literals.

Compiled plans are cached on the statement text, so a parameterized query parses once and
re-binds per execution.

## The SQL escape hatch

Anything the builder can't express can be written as SQL against the same optimizer and executor.
The `sql` tag turns interpolations into bound parameters — arrays expand to IN-list placeholders,
nested fragments splice with their parameters renumbered:

```ts
import { sql } from "@minnowdb/core";

const rows = await sql<{ n: number }>`
  SELECT COUNT(*) AS n FROM people WHERE city IN ${["London", "DC"]}
`.execute(db);
// Compiles to: SELECT COUNT(*) AS n FROM people WHERE city IN ($1, $2)
```

`query()` remains the raw read-only SQL API; every call observes the latest committed state.

### Cached results

Repeating a statement over data that hasn't changed is cheap: the engine keeps computed results —
whole statement results, and the materialized forms of derived, CTE, and windowed sources — keyed
by the exact set of visible segments. Any commit moves that key, so a cached answer is only ever
served when it is provably identical to re-running the query. You never get a stale row.

Pass `memoize: false` when you want the work done rather than the answer reused:

```ts
const rows = await database.query(sql, { memoize: false });
```

That is what the [benchmarks](/benchmarks/) do — replaying one statement over unchanging data with
caching on measures a cache lookup, not query execution. Block and vector caches stay warm either
way; those cache storage reads, not results.

### Locating a compile error

SQL that fails to compile throws a `SqlCompileError` carrying the position of the token that
failed, so an editor can underline it. `offset` and `length` index the exact string you passed —
leading whitespace included:

```ts
import { SqlCompileError } from "@minnowdb/core";

const text = "SELECT * FROM people WHERE name = 'unclosed";

try {
  await database.query(text);
} catch (error) {
  if (error instanceof SqlCompileError) {
    // "'unclosed" — Unterminated string literal
    console.log(text.slice(error.offset, error.offset + error.length), error.message);
  }
}
```

Syntax errors point at the exact token. Errors raised once a block has parsed — a function called
with the wrong number of arguments, say — point at the token that follows it. `length` is 0 where
the failure has no width, such as a query that ends early. Failures after compilation succeeds
(plan optimization, execution) carry no position and stay plain `TypeError`s.

`SqlCompileError` extends `TypeError` and survives the worker channel, so positions arrive intact
on `MinnowDatabaseClient` too.

> Writes get the same treatment — `insertInto` / `updateTable` / `deleteFrom` with `returning`,
> in [Writes & transactions](/docs/writes/). The full supported-SQL list is the
> [feature matrix](/docs/sql/), which covers the surface a query builder emits end to end:
> parameters everywhere including LIMIT/OFFSET, quoted identifiers, FROM-less SELECT, CAST, the
> standard scalar/window/aggregate function core with FILTER and DISTINCT, set operations with
> ALL, upserts including partial DO UPDATE, and correlated subqueries (equality-correlated, in
> WHERE conjuncts, the select list, and ORDER BY — they decorrelate into joins at compile time).
> The SQL:2016 grammar rounds it out: `FETCH FIRST … ROWS ONLY` and `OFFSET … ROWS`,
> `BETWEEN SYMMETRIC`, `LIKE … ESCAPE`, quantified comparisons (`> ANY`, `= SOME`, `> ALL`),
> `VALUES` as a standalone statement or table source, `GROUPING SETS` / `ROLLUP` / `CUBE`,
> `INSERT … SELECT`, and `WITH` on mutations, all with `RETURNING`.
> Known limits: correlated NOT IN and non-equality correlation are rejected explicitly, ORDER BY
> must name a selected column, output alias, or ordinal, and the default NULL ordering matches
> SQLite (NULLs first ascending, last descending) with `NULLS FIRST`/`NULLS LAST` to override.
> FULL JOIN desugars into a union of two left joins, so it must be the sole join with an equality
> ON condition. The [deliberate omissions](/docs/sql/#deliberate-omissions) — things that make no
> sense in a browser worker — are documented with reasons.
