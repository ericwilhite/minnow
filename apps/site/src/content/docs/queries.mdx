# Typed queries

<p class="lede">
  A Kysely-style builder: column names autocomplete, row types are inferred, and every query
  compiles to the same plan its SQL equivalent would — never to a SQL string.
</p>

## Setup

The facade wraps a database or the [worker client](/docs/workers/) — the API is identical over
both. Naming the database type `DB` keeps hovers and errors printing `Minnow<DB>` instead of the
expanded schema:

```ts
import { createMinnow, column, schema, table, type InferDatabase } from "@minnowdb/core";

const people = table("people", {
  name: column.string().unique(),
  score: column.number(),
  city: column.string().nullable(),
});
const orders = table("orders", {
  order_id: column.number().unique(),
  person: column.string().references("people", "name"),
  total: column.number(),
});
const appSchema = schema([people, orders]);
interface DB extends InferDatabase<typeof appSchema> {}

await database.migrate(appSchema);
const db = createMinnow<DB>(database, { schema: appSchema });
```

## Selects

```ts
const rows = await db
  .selectFrom("people as p")
  .innerJoin("orders as o", "o.person", "p.name")
  .where("p.score", ">", 10)
  .where((eb) => eb.or([eb("p.city", "=", "London"), eb("p.city", "is", null)]))
  .groupBy("p.name")
  .having((eb) => eb(eb.fn.countAll(), ">", 1))
  .select(["p.name"])
  .select((eb) => [eb.fn.sum("o.total").as("revenue")])
  .orderBy("revenue", "desc")
  .limit(10)
  .execute(); // Array<{ name: string; revenue: number | null }>
```

The conventions:

- **String left-hand sides are columns; right-hand sides are values.** To compare two columns,
  use `eb.ref("a.x")` or a join's `onRef`.
- **`select()` takes strings, an expression callback, or both** across repeated calls —
  `"p.name"`, `"p.name as owner"`; `selectAll()` is `SELECT *`.
- **Left-joined columns type as `| null`**, because that's what a left join returns.
- **Run with** `execute()`, `executeTakeFirst()`, `executeTakeFirstOrThrow()`; `compile()` gives
  the plan, [`.live()`](/docs/live-queries/) subscribes to it.

## Expressions

| Category         | Forms                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Comparisons      | `eb(lhs, op, rhs)` with `=`, `!=`, `<`, `<=`, `>`, `>=`, `like`, `not like`, `in`, `not in`, `is`, `is not`; `eb.between`, `eb.notBetween` |
| Boolean logic    | `eb.and([...])`, `eb.or([...])`, `eb.not(...)`                                                                                             |
| Arithmetic       | `eb(lhs, "+" \| "-" \| "*" \| "/", rhs)`, `eb.neg(...)`                                                                                    |
| Aggregates       | `eb.fn.count`, `countAll`, `sum`, `avg`, `min`, `max`; `fn.count(x).distinct()`                                                            |
| Scalar functions | `eb.fn.round`, `coalesce`, `dateTrunc`                                                                                                     |
| Windows          | `eb.rowNumber() / rank() / denseRank()` and aggregate `.over((o) => o.partitionBy(...).orderBy(...))`                                      |
| Conditionals     | `eb.case().when(...).then(...).else(...).end()`                                                                                            |
| Subqueries       | `eb.selectFrom(...)`, `eb.exists(...)`, and builders as `in` / comparison operands                                                         |

Result types don't lie: `sum` over an empty group is `null`, so its type is `number | null`.

## Derived tables, CTEs, set operations

```ts
const spend = db
  .selectFrom("orders")
  .groupBy("person")
  .select((eb) => [eb.ref("person").as("person"), eb.fn.sum("total").as("total")]);

// As a derived table…
await db.selectFrom(spend.as("t")).where("t.total", ">", 10).select(["t.person"]).execute();

// …or as a CTE, joinable by name.
await db
  .with("spend", () => spend)
  .selectFrom("people as p")
  .innerJoin("spend", "spend.person", "p.name")
  .select(["p.name", "spend.total"])
  .execute();

// Set operations chain left to right; member row types must match.
await db
  .selectFrom("people")
  .select(["name"])
  .unionAll(db.selectFrom("orders").select(["person as name"]))
  .orderBy("name")
  .execute();
```

Derived and CTE columns stay fully checked — an unknown column on `"t."` is a compile error, same
as on a real table.

## One plan, two front ends

The builder and the SQL parser meet in the same plan-assembly code, so a builder query and its SQL
equivalent produce **identical** optimized plans — same validation errors, same rewrites, same
execution. Plan-equality tests enforce this shape by shape.

```
SQL -> lexer -> parser ----------------+
                                       +-> shared assembly -> optimizer -> physical plan
Typed builder -> compile() ------------+
```

## The SQL escape hatch

Anything the builder can't express can be written as SQL against the same optimizer and executor.
The `sql` tag renders interpolations as SQL literals — strings escape their quotes, arrays become
IN lists, nested fragments splice:

```ts
import { sql } from "@minnowdb/core";

const rows = await sql<{ n: number }>`
  SELECT COUNT(*) AS n FROM people WHERE city IN ${["London", "DC"]}
`.execute(db);
```

`query()` and `prepareQuery()` remain the raw read-only SQL API.

> Writes get the same treatment — `insertInto` / `updateTable` / `deleteFrom` with `returning`,
> in [Writes & transactions](/docs/writes/). The full supported-SQL list is the
> [feature matrix](/docs/sql/). Known limits: correlated subqueries compile but fail at execution
> (subqueries resolve at one snapshot), and ORDER BY must name a selected column or output alias.
