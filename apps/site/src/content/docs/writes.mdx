# Writes & transactions

<p class="lede">
  Two layers, one pipeline: typed mutation builders on top, batch writes underneath. Every write
  validates before it stores anything, and published data is never edited in place.
</p>

## Typed writes

The [query builder](/docs/queries/) carries the write side too, with Kysely conventions:
`execute()` resolves to an array, and the single-result calls are `executeTakeFirst()` /
`executeTakeFirstOrThrow()`.

```ts
const { numInsertedRows } = await db
  .insertInto("people")
  .values([{ name: "Ada", score: 10 }]) // omitted nullable columns pad with null
  .executeTakeFirstOrThrow();

// returning() rewrites the result type to the projected rows.
const written = await db
  .insertInto("people")
  .values({ name: "Grace", score: 20 })
  .returningAll()
  .executeTakeFirstOrThrow(); // { name: "Grace", score: 20, joined: null }

await db.insertInto("people").values({ name: "Ada", score: 99 }).orReplace().execute(); // upsert

const bumped = await db
  .updateTable("people")
  .set((eb) => ({ score: eb("score", "+", 1) })) // or set("score", 5)
  .where("joined", "is", null)
  .returning(["name", "score"]) // post-update values
  .execute();

const removed = await db
  .deleteFrom("people")
  .where("score", "<", 10)
  .returningAll() // the deleted rows
  .execute();
```

Worth knowing:

- **`set({ ...patch })` skips `undefined` entries** — a spread-patch never accidentally nulls a
  column. Explicit `null` still writes NULL.
- **`returning` is exact.** Inserts echo the written rows (there are no defaults or generated
  columns to surprise you); updates return post-update values; deletes return the rows as read.
- **A competing writer fails your statement with a typed error** instead of interleaving.
- **Counts are plain numbers** (`numInsertedRows: number`), not bigints.

Everything below is the batch layer the builders compile onto — use it directly for bulk loads or
when you don't need compile-time types.

## Creating tables

A table uses the four column types, may name one non-null column as its unique key, and may mark
columns `nullable`:

```ts
await database.createTable({
  name: "people",
  uniqueKey: "name",
  columns: [
    { name: "name", type: "string" },
    { name: "score", type: "number" },
    { name: "joined", type: "datetime", nullable: true },
  ],
});
```

## Batch writes

Rows in, one commit out. Inserts validate names, types, nulls, and row counts before anything is
stored:

```ts
const result = await database.insertBatch("people", [
  { name: "Ada", score: 10, joined: new Date() },
  { name: "Grace", score: 20 }, // nullable columns can be left out
]);

await database.upsertBatch("people", [
  { name: "Grace", score: 25, joined: new Date() },
  { name: "Katherine", score: 30, joined: new Date() },
]);

await database.updateBatch("people", {
  keys: ["Grace", "Katherine"],
  changes: { score: [26, 31] },
});

await database.deleteBatch("people", { keys: ["Ada"] });
```

- **`upsertBatch`** updates rows matching the unique key and inserts the rest.
- **`updateBatch`** writes only the key and the changed columns; missing keys are rejected.
- **`deleteBatch`** deletes by unique key.
- A column no row mentions is an error, not a null fill — omitting `score` entirely fails with
  `Missing column: score`. Leaving it out of _some_ rows writes null there, which a non-nullable
  column rejects.
- Every result carries metrics: rows, blocks, bytes, timings, retries, rows per second, write
  amplification.

### The columnar form

The engine stores columns, so `insertBatch` and `upsertBatch` also take a batch that is already
pivoted. It skips building a row object per row — worth it for bulk loads, and for data that
arrives as columns already:

```ts
await database.insertBatch("people", {
  columns: {
    name: ["Ada", "Grace"],
    score: [10, 20],
    joined: [new Date(), null],
  },
});
```

Every column must be present and every array the same length; there is no padding here. Both
forms take the same validation and the same commit path.

## Reading tables

`readTable` takes a column projection and, optionally, a historical version:

```ts
const scores = await database.readTable("people", {
  columns: ["name", "score"],
});
```

## Buffered writer

For event streams: rows go in one at a time, batches come out at a row, byte, or age limit.

```ts
const writer = database.bufferedWriter("people", {
  mode: "upsert",
  maxRows: 1_000,
  maxBytes: 1024 * 1024,
  maxAgeMs: 1_000,
});
await writer.add({ name: "Linus", score: 30, joined: new Date() });

writer.requestFlush(); // non-blocking; failures go to onError
await writer.close();
```

An age-triggered flush drains everything accepted so far, even rows that arrived while a previous
batch was committing. `attachLifecycleFlush()` requests a flush when the page hides.

> Lifecycle flushing is an optimization, not a durability guarantee. Durability ends at a
> committed IndexedDB transaction — browser shutdown can't be made reliable by page events.

## Maintenance

Compaction, garbage collection, and spill cleanup all advance in small, durable, resumable steps.
A tab dying mid-job costs one step, not the job.

```ts
// Advance a compaction one output block at a time.
let progress = await database.compactTableStep("events", { maxBlocks: 1 });
while (progress.result === null) {
  if (progress.jobId === null) throw new Error("Expected a compaction job");
  progress = await database.resumeCompactionJob(progress.jobId, { maxBlocks: 1 });
}

// Reclaim unreachable history — in one call, or step by step.
const collection = await database.collectGarbage({ maxItemsPerStep: 64 });
let gcProgress = await database.collectGarbageStep({ maxItems: 8 });

// Reclaim spill pages abandoned by dead tabs, once their leases expire.
const spillCleanup = await database.cleanupQuerySpill({ maxOwners: 64 });
```

- **`compactTable()`** runs to completion; **`compactTableStep()`** advances by at most
  `maxBlocks`; **`resumeCompactionJob()`** continues after a yield or reopen;
  **`listCompactionJobs()`** shows what's persisted.
- **`cancelCompactionJob(jobId)`** settles a job as cancelled, atomically — either the cancel
  wins or the publish already did, and the result tells you which. Idempotent.
- **Garbage collection is reachability-based:** the current manifest, unexpired leases, active
  transactions, and running compactions are the roots; everything else with known provenance is
  reclaimable.
- **Cancellation is cooperative** — an in-flight step notices at its next durable boundary, and
  a cancelled job's blocks wait for a later GC pass.

See [Schema & migrations](/docs/schema/) for the typed alternative to `createTable`, and
[Best practices](/docs/best-practices/) for when to schedule maintenance.
