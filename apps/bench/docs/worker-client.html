Run it in a worker

The library ships both sides of the worker channel: a ready-made worker entry (@browserdatabase/engine/worker) and a main-thread client (@browserdatabase/engine/client). Your application contributes exactly one line — constructing the Worker — because that is the only line your bundler must be able to see.

Quick start

import { BrowserDatabaseClient } from "@browserdatabase/engine/client";
import { BrowserDb, column, schema, table, type InferDatabase } from "@browserdatabase/engine";

const people = table("people", {
  name: column.string().unique(),
  score: column.number(),
});
const appSchema = schema([people]);

const client = new BrowserDatabaseClient(
  new Worker(new URL("@browserdatabase/engine/worker", import.meta.url), { type: "module" }),
  { store: { kind: "indexeddb", name: "app-db" } },
);
await client.migrate(appSchema);

// The typed facade wraps the client exactly as it wraps an in-worker database.
const db = new BrowserDb<InferDatabase<typeof appSchema>>(client, { schema: appSchema });
await db
  .insertInto("people")
  .values([
    { name: "Ada", score: 10 },
    { name: "Grace", score: 20 },
  ])
  .execute();
const rows = await db
  .selectFrom("people")
  .select(["name", "score"])
  .orderBy("score", "desc")
  .execute(); // Array<{ name: string; score: number }>

The client sends its configuration to the worker in an init frame, so the stock entry needs no configuration of its own. Because the channel is ordered you may issue calls immediately; await client.ready() exists when you want to surface store-open failures eagerly. IndexedDB access, block decoding, planning, and query execution all run in the worker; the main thread holds only this proxy. The client also exposes the raw layer directly — client.query(sql), client.insertBatch(...), client.createTable(...) — mirroring the full database API.

Why you construct the Worker

A worker needs a script URL at runtime, and new Worker(new URL("…", import.meta.url), { type: "module" }) is only rewritten correctly when your bundler sees that exact expression in your build graph. Buried inside a published library it degrades differently under every bundler — which is why the one bundler-sensitive line lives in your code. It also keeps lifecycle ownership honest: you decide when the worker is created, shared, and terminated, and content-security policies (worker-src) are satisfied by your origin rather than worked around with blob URLs.

What changes across the boundary

  • Every member is asynchronous. Members that are synchronous in the worker (PreparedQuery.execute(), stats getters, close()) return promises on the client, and getter pairs become methods — writer.stats(), prepared.memoryUsage().
  • prepareQuery() still pins one leased snapshot in the worker until close(), but a client-side execute() measures execution plus one channel round trip — benchmark inside the worker when isolating executor time.
  • migrate() accepts the same schema DSL (serialized over the wire automatically) and reports its steps in a data-only wire form.
  • Typed errors are rehydrated on the client: instanceof UniqueConstraintError works and carries its fields; stack traces point into the worker.
  • Construction options that are functions (now, createId, a custom store) cannot cross the channel — use a custom entry (below).

The typed facade is unaffected by all of this: compiled plans and statements cross the channel by structured clone, so selectFrom, the typed writes with returning, and .live() behave identically on the main thread.

Buffered writers and live queries

Stateful handles proxy transparently: the writer's age timer runs on the worker's clock, and live-query callbacks arrive as events. Cross-tab commit hints work by naming a BroadcastChannel the worker should join. 

const writer = client.bufferedWriter("people", {
  maxRows: 500,
  onError: (error) => console.error("background flush failed", error),
});
await writer.add({ name: "Edsger", score: 30 });
await writer.close();

const live = client.liveQueries({ channelName: "app-db-commits" });
const subscription = await live.subscribe(
  "SELECT name, score FROM people ORDER BY score DESC",
  { onChange: (result) => render(result.rows) },
);
// … later
await subscription.close();
await live.close();
await client.close({ terminateWorker: true });

Bundler setups

Vite and webpack 5 both understand the quick-start pattern as written — they see the new URL("@browserdatabase/engine/worker", import.meta.url) expression, resolve the package subpath, and emit a separate worker chunk. Nothing else is required.

esbuild (and Parcel 2 with default settings) does not rewrite new URL worker expressions. Build the worker entry as its own bundle and point the Worker at the emitted file: 

// worker.ts — your one-line worker entry, bundled separately:
import "@browserdatabase/engine/worker";

// esbuild app.ts worker.ts --bundle --format=esm --outdir=dist --splitting

// app.ts:
const client = new BrowserDatabaseClient(
  new Worker(new URL("./worker.js", import.meta.url), { type: "module" }),
);

No bundler — module workers cannot resolve bare specifiers (import maps do not apply inside workers in all engines yet), so use full URLs from your chosen CDN or vendored files: 

// db-worker.js — served from your origin:
import "https://cdn.example.com/@browserdatabase/engine/dist/worker.js";

// main page:
import { BrowserDatabaseClient } from "https://cdn.example.com/@browserdatabase/engine/dist/client.js";
const client = new BrowserDatabaseClient(
  new Worker(new URL("./db-worker.js", import.meta.url), { type: "module" }),
);

Custom worker entries

The stock entry covers the cloneable configuration surface: the store descriptor (indexeddb or memory) plus compression, rowsPerBlock, maxCommitRetries, and spillOwnerLeaseMs. When construction needs things a message cannot carry — a custom BlockStore, deterministic now/createId seams — write your own entry and expose the database you built: 

// my-worker.ts
import { BrowserDatabase, exposeDatabase } from "@browserdatabase/engine";
import { IndexedDbBlockStore } from "@browserdatabase/storage-idb";

const store = await IndexedDbBlockStore.open({ name: "app-db", durability: "strict" });
exposeDatabase(new BrowserDatabase(store, { compression: "gzip" }), self, {
  onDispose: () => store.close(),
});

exposeDatabase() answers the same client frames, acknowledging the client's init without reconstructing anything, so the main-thread code is unchanged. Underneath both entries sits @browserdatabase/worker-protocol: versioned, structured-clone-safe RPC frames with method whitelists per handle — the worker never dispatches arbitrary property access.

The worker changes where work runs, not the durability contract: correctness never depends on BroadcastChannel, Web Locks, page-close handlers, or successful background work. IndexedDB is authoritative, and the contract still ends at a successfully committed IndexedDB transaction.
